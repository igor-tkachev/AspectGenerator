# Agent Instructions

Before working on AspectGenerator hardening, diagnostics, code generation, or incremental generator refactors, read `docs/AspectGeneratorHardeningPlan.md`.

Current notes:

- Invocation discovery should stay on `SyntaxProvider` candidates. Do not reintroduce full syntax-tree scans through `CompilationProvider` + `DescendantNodes()`.
- Keep `InterceptMethods` diagnostics deferred unless the user explicitly asks to work on them.
- Preserve CRLF line endings for touched repository files.
- Do not add new NuGet packages, template engines, formatters, source-generation helper libraries, or build tools unless the maintainer explicitly asks for that dependency.
- Do not replace internal code generation with Scriban, Handlebars.Net, CSharpier, or other external templating/formatting tools as an automatic refactoring step.

## Target filter parser

The target filter language is read by a parser written in DotGram, from the grammar `Source/FilterV2/FilterV2.gram` into the tree of `FilterV2Syntax.cs` by `FilterV2Reader`, and generated ahead of the build. The generated C# in `Source/TargetFilter/Generated` is committed and compiled like any other source: the build and the package have no DotGram dependency, and nothing is generated at build time. Its tests are under `UnitTests/Tests/FilterV2`, and `Baselines/FilterV2/corpus.txt` pins its reading of the corpus there (`AG_UPDATE_BASELINES=1`).

What a filter means is decided in three more parts, and together they are what selects targets. `Source/TargetFilterFacts` reads the facts of a method from its symbol, on demand. `Source/TargetFilterBinding` turns the tree of a filter into a block of conditions: `FilterBlockBuilder` makes the checks that need the whole filter (a property included twice, `any` beside another condition, a reference in a compound part or to a level that is not above the block), compiles every pattern into a matcher over the structure of names and types (`NamePattern`, `TypePattern`; `IMethodFacts` is all a condition reads, over symbols or over records written by hand), and names what a call has to satisfy before it is worth binding (`BindingAnchors`). `Source/Cascade` decides from the blocks of an aspect whether a method gets it and with which settings. `Source/Selection` builds the blocks from the attributes of every level and `AspectSelectionService` runs the cascade. A condition describes the call: a decision is asked of the definition of a method first and of each call only where a pattern names a type in the place of a type parameter (`FilterTarget`). Their tests are under `UnitTests/Tests/Selection`, `UnitTests/Tests/TargetFilterBinding`, `UnitTests/Tests/Cascade` and `UnitTests/Tests/TargetFilters/MethodFactsTests.cs`; `UnitTests/Tests/Cascade/CascadeCases.json` is run both by the cascade alone and from real filter text. The generated parser compiles against Roslyn 4.12 on `netstandard2.0`, and the `minimum-sdk` consumers run it in the SDK 9.0.100 compiler through their `TargetFilter`.

`Baselines/TargetFilters/*.txt` are the decisions of the earlier filter language over its corpus, kept as frozen data. Nothing regenerates or reads them any more (the code that wrote them is gone); they stay so that a later comparison of the old selections with the current ones has the old side. Do not edit, regenerate or delete them.

- The grammar reads a line in stages: a line, then each piece of it (a condition, a value, a name, a method pattern, a parameter list), each a publication read over the trimmed piece. Keep that shape when changing the language, and run the corpus tests: a baseline difference is either a defect of the change or an intended change that needs re-accepted baselines (`AG_UPDATE_BASELINES=1`), with every changed record explained in the commit.
- The generated parser can carry a reading nested deeper than its stack over to a thread of its own; `FilterV2Parser.OnHandingOff` refuses that (the generator runs on the compiler's threads), and such a filter is reported as nested too deeply. That code reads the thread's cultures, which RS1035 bans in analyzers; the generated file carries its own narrow `#pragma warning disable RS1035` around those reads.

- After any change to `FilterV2.gram` (or to a type it builds), run `Source/TargetFilter/regenerate.sh` and commit the changed files with it. Never edit `Generated` by hand; the next run overwrites it. The script works in Git Bash on Windows too.
- `Source/TargetFilter/dotgram.pin` names the DotGram commit and the exact .NET SDK the generation uses. The script builds `DotGram.Cli` at that commit into a scratch folder (`DOTGRAM_SCRATCH`, `DOTGRAM_REPO` to fetch from a local clone) and refuses to run under another SDK: select the pinned one first, for instance with an untracked `global.json` (the refusal message prints it). Move the pin only to a green commit of the DotGram repository, in a commit of its own with the regenerated folder.
- The `filter-parser` CI job runs the same script and fails when `git status` shows any difference in `Source/TargetFilter`. The script itself fails when `Generated` holds a file the manifest (`.dotgram.json`) does not list, which the generator would leave in place. `.gitattributes` keeps `*.gram` and scripts at LF and the generated folder byte for byte (`-text`, last rule).
- `-p:DotGramLocal=true -p:DotGramRoot=<a DotGram checkout>` builds the parser from the grammar with that checkout as the generator and leaves the committed folder out (default `DotGramRoot` is `..\dotgram`, next to this repository). It is for trying a DotGram change; the committed folder is what ships. In this mode automatic packaging is off and an explicit `dotnet pack` fails, so a package never carries an unpinned parser.
