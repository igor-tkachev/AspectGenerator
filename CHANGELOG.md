# Changelog

## 1.1.2 — Unreleased

- Fixed generated interceptors with multiple aspects and async hooks emitting duplicate `async` modifiers; non-generic `Task` and `ValueTask` targets are now awaited before running completion hooks.
- Fixed `OnCall` ordering diagnostics to use the same `Order`-sorted aspect chain as grouping and code generation.
- The minimum-SDK CI consumers now use the project package version and verify the restored package matches the locally packed bytes.
- Documented that `TargetFilter` is compile-time metadata and is not copied to runtime aspect instances, and that Static-lifetime instances are shared across threads and construction failures surface as `TypeInitializationException`.
- Ship the AspectGenerator agent guide as the discoverable `aspectgenerator` skill under `skills/aspectgenerator/`, with YAML frontmatter, a short entry point and focused task guides. Remove the former package-root `SKILL.md`; validate the packed skill metadata and relative links in CI.

## 1.1.1 — 2026-11-05

- Fixed interceptors that did not compile because they named something they cannot access. Calls to members of file-local types (`file class`) are now left as they are and reported with `AG0003`, like calls to private and protected targets: the compiler counts a file-local type as accessible within the assembly, but the generated file cannot name it. The same now holds for the aspect side: an aspect type that is private, protected or file-local, an attribute constructor the generated code cannot access, an enum or `typeof` argument of such a type, a type argument of a generic aspect that cannot be named, and a hook method that is private or protected (the hooks are checked as the interceptor of that call uses them: an async hook a synchronous call never calls does not count). Before, each of these failed the build with `CS0122` or `CS0400` in `Interceptors.g.cs`. A file-local type argument of a generic call gets a generic interceptor, as a private nested one does.
- Changed: an aspect applied to a type or the assembly with a `TargetFilter` whose arguments include an enum or `typeof` of a type the generated file cannot name (a private nested enum, for example) is no longer intercepted; the calls are reported with `AG0006`/`AG0007` (information). Before, the interceptor passed such an enum as its number and compiled.
- Fixed hook overloads: the interceptor calls the accessible overload the hook checks resolved. Before, a private overload that takes the aspect (`Before(MyAspect aspect, InterceptInfo info)`) next to a public `Before(InterceptInfo info)` made the generated call pass the aspect, which did not compile (`CS1501`). Static hooks declared in a base class of the aspect are found, as the generated call finds them (a public one no longer gets `AG0101`), and a hook whose aspect parameter has a base type of the aspect (a hook on a generic base aspect) is accepted. When a hook the interceptor would call fails its check in a way the generated call cannot compile (missing, not static, a parameter list that does not fit, an `OnCall` mismatch, or a return type `OnInit`, `OnUsing` or an async hook cannot use), that aspect is left out of the interceptor for that target, so the build reports the AG01xx error instead of compiler errors in `Interceptors.g.cs`. The other aspects of the target still apply, which matters when the diagnostic's severity is lowered; a synchronous hook that returns a value is called as a statement and stays; `AG0101` for an aspect of a referenced assembly says the hook may exist but not be accessible (metadata does not show this assembly the internal members of another without `InternalsVisibleTo`).
- Fixed generic aspect attributes declared in the project (`[Log<int>]` with `[Aspect]` on `LogAttribute<T>`): their calls were not intercepted and nothing was reported. A generic aspect from a referenced assembly was intercepted before and still is.
- New warning `AG0108`: an aspect with `OnAfterCall`, `OnCatch`, `OnFinally` or `OnUsing` on an iterator method (`yield`, sync or `IAsyncEnumerable<T>`). The call of an iterator only creates the sequence, so these hooks run before the iterator body, and an exception thrown while the sequence is enumerated never reaches `OnCatch`. Before, such an aspect guarded nothing and nothing said so. The warning is reported once per aspect application, at the aspect applied to the method (information at the call when only a target filter selected it). For a virtual, abstract or interface method it is decided on what the call can run: the method's own body and every override or implementation in the project; see [Hook lifecycle](docs/wiki/Hook-lifecycle.md#iterators).
- Fixed the aspect instance the interceptor constructs from the applied attribute: it now receives every argument with the type the attribute holds. An enum, `byte`, `sbyte`, `short` or `ushort` passed to an `object` parameter or property, or inside an `object[]`, arrived as an `int`; a nested array or `typeof` inside an `object[]` made the generator fail, so no aspect was applied at all; a negative enum value did not compile; an `object`-typed `null` constructor argument made the copy bind to another constructor overload; and an aspect applied to a type with a `TargetFilter` got its `typeof` arguments as `null` and its array arguments as code that did not compile.
- `AG0104` (invalid hook return type) names the return type the hook needs. For an async hook on a target framework without `ValueTask` (.NET Framework, or netstandard2.0 without `System.Threading.Tasks.Extensions`), it names the target framework and says that only `Task` is available there. A hook whose return type the compiler cannot resolve no longer gets `AG0104` on top of the compiler's `CS0246`.
- Changed: which host runs the generator now decides between a build and the editor's live analysis, before the MSBuild properties do. The compiler (`csc`, `VBCSCompiler`) always builds, so a `DesignTimeBuild=true` left set by a project no longer turns a real build into a design-time one. Every host that is not a known editor builds as well: `dotnet watch`, generator test harnesses (`Microsoft.CodeAnalysis.Testing`), tools on `AdhocWorkspace` or `MSBuildWorkspace`. Before, such a host ran at design time whenever its project evaluation said `DesignTimeBuild=true` (an `MSBuildWorkspace` always does), and the compilation it emitted silently had no aspects; `dotnet watch` Hot Reload lost the aspects of every edited method that way. Only the known editors — Visual Studio 2022 and 2026, the C# language server of VS Code — follow the properties: `DesignTimeBuild=true` without `BuildingProject=true` is the live analysis, which selects no targets and binds no calls. After a real build the editor reads `BuildingProject=true` from `obj/.../<Project>.GeneratedMSBuildEditorConfig.editorconfig` (every build rewrites it) and builds on purpose until the next design-time build: Hot Reload and Edit and Continue in Visual Studio emit their delta from the editor's compilation, and a delta without interceptors drops the aspects of the edited method with no error shown. The build report gains a `Generator host` row; an editor never writes the report (before, Visual Studio 2022 and 2026 overwrote the compiler's report after a build, at times with a partial one). An editor the generator does not know runs the full analysis on every generator run; its name is in the `Generator host` row. See [Diagnostics](docs/wiki/Diagnostics.md#design-time-builds).
- Changed: the `AG0300` analyzer skips the generator's own `Interceptors.g.cs` when it selects targets. The generator never sees that file, so the analyzer now selects exactly what the generator did; in the editor after a build (the compilation then carries the generated interceptors, 5 MB for 24,000 call sites) the analyzer's cost per edit drops from about 0.6–0.9 s to about 0.15 s, the level of the live analysis.

## 1.1.0 — 2026-11-04

- Changed: `AG0006` (a call that only a target filter selected and that is left as it is) is off by default, and the new `AG0007` (information, no source location) reports one summary per reason with the number of such calls. Every diagnostic reported at a source location makes the compiler bind the enclosing method again to look for `[SuppressMessage]`, several milliseconds each; with `namespace: LinqToDB.**` on linq2db, 11,396 `AG0006` reports took the generator from about 25 s to about 70 s per build and allocated about 7 GB more. To list the calls with their locations, set `dotnet_diagnostic.AG0006.severity = warning` in `.editorconfig` (`suggestion` shows them in the IDE and a binary log only: a command-line build does not print information diagnostics). `AG0007` is not printed by a command-line build either; it has no location, so its severity is set in a global config (`is_global = true`), or with `NoWarn` / `WarningsAsErrors`. `AG0003` for calls to methods that carry the aspect themselves is reported per call as before.
- Changed: design-time builds (the IDE's live analysis, `DesignTimeBuild=true`) no longer select target methods or bind calls; they only compile the target filters. On a large project, in a driver configured as the IDE configures it, the generator drops from seconds to tens of milliseconds per edit, independent of the filters used. Target filter errors (`AG0201`, `AG0202`, `AG0204`–`AG0206`, `AG0208`), the options check `AG0209`, and `AG0101`/`AG0102` for aspects declared in the project are still reported live. The checks that need a selected target method or a bound call are now reported by builds only: `AG0001`, `AG0002`, `AG0003` and `AG0006` (calls left as they are), `AG0103`–`AG0107`, and `AG0101`/`AG0102` for aspects declared in referenced assemblies. See [Diagnostics](docs/wiki/Diagnostics.md#design-time-builds).
- Changed: the package is now a development dependency (`<DevelopmentDependency>true</DevelopmentDependency>`). `dotnet add package AspectGenerator` adds it with `PrivateAssets="all"`, and it no longer appears as a dependency of a package that references it. Before, a normal `PackageReference` flowed transitively to the consumers of a library; there the analyzer ran without the package's `build/*.props` (`InterceptorsNamespaces` and the generator options), which silently dropped aspects or broke interceptors. A library author who relied on the package flowing to consumers either writes `PrivateAssets="none"` on the reference (the generator then flows, with its props) or references AspectGenerator directly in every project where it is used. Existing references without `PrivateAssets="all"` should add it, or write `PrivateAssets="none"` to keep the flow (omitting `PrivateAssets` also flows; only `all` keeps the package private).
- The props and targets are shipped in `buildTransitive/` as well as `build/` (which forwards to it). NuGet imports `buildTransitive/` in place of `build/`, so a generator that flows transitively brings `InterceptorsNamespaces` and the options with it, and a direct reference imports them once.
- Breaking (narrow): `AspectGeneratorGenerateApi` no longer defaults to `true` in the props. When it is unset and a referenced assembly already declares a public `AspectAttribute`, the project uses that API instead of generating a second copy. This affects MSBuild conditions on `$(AspectGeneratorGenerateApi)` (now empty), apps that relied on their own internal API copy and now bind to the library's types, and version skew where newer attribute members meet an older library API. Set the property to `true` explicitly to restore the previous behavior.
- New warning `AG0005`: the generator intercepts calls in a project whose build props were not imported (a transitive analyzer without props, or a manual analyzer reference). It adds one warning that names the cause next to the compiler's interceptor errors, and replaces `AG0004` in that case. Projects wired by hand with `InterceptorsNamespaces` set are not affected.
- Documentation: new wiki page "Using AspectGenerator in libraries" with a table of the library and application scenarios.
- The package contains only the analyzer (`analyzers/dotnet/cs`) and the build props and targets; it has no `lib` assembly.

- Documented the minimum build toolchain: .NET SDK 9.0.100 or later (Roslyn 4.12; Visual Studio 2022 17.12 or later). The generator is built against Roslyn 4.12, so any newer compiler loads it; an older one (SDK 8.0.x, Visual Studio before 17.12) reports `CS9057` and does not load it, so aspects are not applied. Consumers that target `net8.0` work when built with such an SDK.
- Selected target methods are found from their declarations before call sites are bound, and call sites are rejected by name, generic arity and argument count before binding. Semantic models are reused per syntax tree. Together this makes the generator several times faster on large projects.
- Fixed calls that were not intercepted under declaration-first selection: instance-form extension method calls (`"a".Ext()`, `items.Count()` with inferred type arguments, `text?.Ext()`), calls through a PascalCase property or field, static calls through a derived type or a `using` alias, and assembly-level native `TargetFilter` patterns that select methods of referenced assemblies (for example `public static System.Math.Max(System.Int32, System.Int32)`), and compiler-generated record methods (`ToString`, `Equals`, `GetHashCode`) selected by assembly-level or type-level filters.
- `AG0300` markers now use the generator's selection plan, so they are reported exactly for the intercepted calls, and the marker analyzer no longer binds every invocation.
- Generated interceptors use fully qualified (`global::`) type names. Aspect attributes declared in the global namespace or nested in a class no longer produce code that does not compile.
- Calls with explicit type arguments (`M<T>()`) and conditional calls (`a?.M()`) are intercepted; the generated code no longer contains `#error` for them.
- Fixed interceptors that did not compile, found by applying aspects to a large code base: a call that spans several lines (or an aspect whose `TargetFilter` does) is no longer echoed into a generated comment with its line breaks, which turned the rest of the text into code.
- Calls whose type arguments cannot be named in generated code (type parameters of the calling method or type, anonymous types, private nested types) get a generic interceptor over the target's type parameters with the same constraints, one per target and aspect list.
- Fixed interceptors for static-form extension calls (`Extensions.Ext(value)`), `out` parameters (including a record's generated `Deconstruct`, which target filters now select), non-generic `Task` and `ValueTask` targets without async hooks, `dynamic` parameters, ref struct parameters such as `params ReadOnlySpan<T>`, pointer and function pointer parameters (the interceptor is `unsafe`), instance methods of structs (the interceptor takes `this ref`, or `this in` for a readonly member), extension methods with `this ref`, `this in` or `this ref readonly` (the receiver is passed on by reference), and static methods of constructed generic types.
- Calls inside expression trees (lambdas converted to `Expression<T>`, query clauses over `IQueryable`) are no longer intercepted: a query provider must see the original method. Before, a target filter could select them, and the compiler failed.
- `base.M()` calls are no longer intercepted: the interceptor called the method through its receiver, so a virtual target recursed into the override.
- Calls that still cannot be intercepted (local functions, members of C# 14 extension blocks, calls removed by `[Conditional]`, `private` or `protected` targets, by-reference, ref struct and pointer returns, static abstract interface members, interface calls on a type parameter that may be a struct, and a few rarer shapes listed in Limitations) are left as they are and reported. Before, they produced code that did not compile.
- New diagnostic `AG0006` (information) for a call that only a target filter selected and that cannot be intercepted. `AG0003` (warning) stays for calls to methods that carry the aspect themselves and for calls the compiler cannot intercept, so the two can be configured separately in `.editorconfig`.
- Documentation: removed machine-specific paths, added the trace properties to the repository build props, and marked the file-local interceptor type as implemented in the roadmap.
